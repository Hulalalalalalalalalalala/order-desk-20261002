# 订单工作台

维护商品价格、计算订单金额，并保存订单与取消状态。金额使用整数分。

## 运行

需要 Python 3.10 或更新版本，仅使用标准库，无依赖安装步骤。请在本目录运行：

```sh
python3 -m order_desk --root ./state demo
python3 -m unittest discover -s tests -v
```

这是本地命令行程序，不监听网络端口，无账户或密码。`demo` 在指定 root 的临时子目录中读取 examples 样例并演示业务，结束后清理样例状态，不改变现有数据。

## 正常使用

公开 API：`from order_desk import OrderDesk`，然后 `OrderDesk(root)`。每个命令接收可选的 JSON 文件，其对象键与 API 方法参数一致。例如：

```sh
python3 -m order_desk --root ./state add-product examples/products.json
```

JSON 数组会按顺序执行多个独立操作；先前成功操作保留，后续失败不会回滚整批。重跑登记命令遇到已存在的标识会报错。

- `add-product` → `OrderDesk.add_product(...)`。参数名见 `core.py` 的公开方法签名。新建商品默认启用销售（`enabled` 为 `true`），但新建时不在数据中写入 `enabled` 字段；仅在显式切换状态时才保存该字段。
- `set-product-enabled` → `OrderDesk.set_product_enabled(sku, enabled)`。暂停或恢复商品销售，仅返回 `{sku, name, price_cents, enabled}`。`sku` 去除首尾空白后匹配并区分大小写，非字符串、空白值或未知商品抛出 `ValueError`；`enabled` 必须是布尔值（`type` 为 `bool`），整数、字符串等不转换为布尔值，否则抛出 `ValueError`。结果与商品同次保存在 `root/data.json`，重新打开一致；重复设置同一状态仍成功；不改变名称、价格、库存、已有订单与历史，也不追加任何订单事件。旧商品缺少 `enabled` 字段时视为启用，设置时才写入该字段。
- `get-product` → `OrderDesk.get_product(sku)`。按 sku 查询商品，仅返回 `{sku, name, price_cents, enabled}`；缺少 `enabled` 字段的旧商品返回 `enabled` 为 `true`，但不补写字段。`sku` 规则同 `set-product-enabled`，非字符串、空白值或未知商品抛出 `ValueError`；查询不创建目录或文件。
- `reprice-products` → `OrderDesk.reprice_products(lines)`。带原价核对的整批调价，一笔请求全部成功或全部拒绝。`lines` 为非空列表，每项是含 `sku`、`expected_price_cents`、`price_cents` 的对象（行内额外字段忽略）：`sku` 为去除首尾空白后的非空字符串，区分大小写；两个价格只接受非负整数分（零价有效），不接受布尔值、字符串或小数。列表类型不符或为空、项目非对象、缺少必要字段、编号非法或未知、价格非法、归一化后编号重复（即使新旧价格都相同也拒绝）、或预期单价与当前目录不符均抛出 `ValueError`。暂停销售和未纳管商品也允许调价，不因此恢复销售或自动纳管；名称、销售状态、库存与预留均不变，旧商品缺少 `enabled` 时仍视为启用且不补写该字段；不新增订单或库存历史、不消耗序号。整批未变价（全部目标价等于原价）时成功但不写文件，也不创建原本不存在的目录；末项失败同样不保留前项变更，文件内容不变。成功返回按 sku 升序的数组，每项仅含 `sku`、`before`、`after`，后两项采用 `get-product` 的完整商品结构，分别反映调价前后的值；目标价等于原价的商品仍返回。有实际变价时整批价格同次保存至 `root/data.json`，重新打开同一 root 后查询一致。调价只影响之后的计价：随后的 `quote`、新下单和购物清单结算按最新目录计价，已保存清单的商品与数量不变；既有订单的商品行、单价、金额及全部历史快照不随调价变化，随后调用 `amend` 仍按其现有规则以提交时目录重算全部商品行，不因原价核对增加限制（商品从 100 分调至 150 分后，原两件订单仍为 200 分，新订单或结算两件为 300 分，原订单成功改为两件后也为 300 分）。
- `restock` → `OrderDesk.restock(sku, quantity)`。补货只增加在库量，不改变预留量；商品首次成功补货后纳管库存。补货不受销售状态影响，暂停商品仍可补货。
- `stock` → `OrderDesk.stock(sku)`。返回 `{sku, on_hand, reserved, available}`；未纳管商品的 `on_hand`、`available` 为 `null`，`reserved` 为 `0`。
- `place` → `OrderDesk.place(...)`。对已纳管商品按合计数量检查并预留可用量（在库量减预留量），任一商品缺货则整笔订单不创建。清单中只要包含一个暂停销售商品（`enabled` 为 `false`，未纳管商品同样适用），整次抛出 `ValueError`，不返回部分预览、不创建订单或预留库存。
- `amend` → `OrderDesk.amend(order_id, lines)`。替换 `placed` 订单的全部商品行，不另建订单，编号与状态不变。`lines` 结构同 `place`，行内额外字段忽略；商品行保留输入顺序与重复 SKU，单价取提交时商品目录，小计与总金额仍为整数分，`get` 与 `list` 返回修改后的内容。同一 SKU 合并数量检查：新需求不得超过当前可用量加该订单实际预留量；成功后各商品预留量等于其他订单预留加本次需求，在库量不变，移除的商品释放其原预留，此后取消或发货只处理修改后的实际预留。未纳管商品仍不限制数量、不生成预留；下单后才纳管的商品按当前库存检查并预留；无预留记录的旧订单不获得额外额度。对暂停销售商品：允许保留、减量或从清单中移除，但不能加入原清单没有的暂停商品，也不能增加该 SKU 的合计数量；比较时分别合并当前订单行与新清单中的重复 SKU，以当前订购量为准，不使用历史数量或实际预留量（原两行合计三件时重排为三件可通过、四件被拒绝；先减为一件后不能再增至两件）。订单不存在或非 `placed`、编号或 SKU 非法、清单非列表或为空、行非对象或缺少 `sku`/`quantity`、数量非正整数或为布尔值、商品未知、库存不足均抛出 `ValueError`，拒绝不改写数据、不消耗历史序号。每次成功提交（含相同清单重复提交）追加 `action` 为 `amend`、`result` 为修改后订单快照的历史事件，旧事件与 `complete` 不变，无历史的旧订单从 1 开始且 `complete` 为 `false`；修改与历史同次写入 `root/data.json`。
- `reserve-order` → `OrderDesk.reserve_order(order_id)`。为下单时尚未纳管的商品补齐订单预留，保留成交内容：仅处理 `placed` 订单，商品行顺序、重复行、成交单价、金额与状态均不变，暂停销售不阻止补齐。`order_id` 为去除首尾空白后的非空字符串（区分大小写）；未知订单、非法编号、非 `placed` 状态或订单商品不在当前目录中均抛出 `ValueError`。按当前商品行合并重复 SKU 计算需求；对已纳管商品按需求减本单实际预留量的非负差额增加预留（缺少预留记录视为零），仅使用当前可用量，任一商品不足则整笔抛出 `ValueError`，不补齐任何商品；未纳管商品不限制数量、不自动纳管，预留仍为零，在库量和其他订单预留不变。返回仅含 `order_id` 和 `lines`，商品行按 SKU 升序覆盖订单全部商品，每行仅含 `sku`、`quantity`、`added`、`reserved`，分别表示编号、合并需求、新增预留量和补齐后本单预留量，未纳管行后两项为零。实际新增预留时，变更与历史同次保存到 `root/data.json`，重新打开一致：订单历史追加 `action` 为 `reserve-order`、`result` 为返回快照的事件，各新增预留商品按既有库存历史结构记录同名 `action`，`reference_id` 为订单编号，前后快照反映预留与可用量变化，序号接续，旧快照与已有 `complete` 不变，缺少历史的旧数据从 1 开始且 `complete` 为 `false`，不补造过去。没有新增量时仍返回结果，但不写文件或追加事件；失败不写文件、不创建目录或消耗序号。补齐后的拣货汇总、改单、取消和单笔及批量发货按原规则使用实际预留。
- `reserve-batch` → `OrderDesk.reserve_batch(order_ids)`。按优先顺序批量执行预留补齐：`order_ids` 的输入顺序即优先级（编号去除首尾空白后区分大小写），逐单判断并执行，规则与 `reservation-plan` 的预览一致，但可补齐的订单会真实新增预留。`order_ids` 为非空列表，归一化后重复编号、类型不符、编号非法（非字符串或空白）、未知订单、状态非 `placed` 或任一订单商品不在当前目录中均使整次请求抛出 `ValueError`：即使问题在末项也不保留前项变更，不改写文件、不创建目录或消耗历史序号。按各订单当前商品行合并重复 SKU，以需求减本单实际预留的非负差额补齐（缺少预留记录视为零），仅使用扣除全部既有预留后的可用量，不释放或转移既有预留；每单全部纳管商品够量才新增，任一不足就整单跳过并继续后续订单，被跳过订单不占用余量；未纳管商品不限制需求、不自动纳管，暂停销售不阻止补齐。结果按输入顺序返回数组，每项仅含 `order_id`、`can_reserve`、`lines`；`can_reserve` 为能否整单补齐的布尔值，已足额订单也为 `true`。商品行沿用 `reserve-order` 的覆盖范围与 SKU 升序规则，每行仅含 `sku`、`quantity`、`added`、`reserved`、`shortfall`：`added` 为实际新增量，`reserved` 为处理后的本单预留，`shortfall` 为轮到本单时新增需求超出可用量的非负差额；被跳过订单各行 `added` 为零，未纳管行 `added`、`reserved`、`shortfall` 均为零。有新增时将整个批次的变更与历史同次保存到 `root/data.json`，重新打开一致；无新增时不写文件或追加事件。有新增量的订单追加 `action` 为 `reserve-order`、`result` 为单笔补齐返回结构（仅含 `order_id`、`lines`，行内无 `shortfall`）的历史事件，各新增预留商品按既有库存历史结构记录同名 `action`，`reference_id` 为订单编号，共用商品的快照按请求顺序衔接，序号接续，旧快照与已有 `complete` 不变，无历史的旧数据从 1 开始且 `complete` 为 `false`，不补造过去。订单状态、成交行、金额、在库量和本批之外订单的预留不变；补齐后的拣货汇总、改单、取消及发货按原规则使用实际预留。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；整批一致性只限单个 `order_ids` 请求。
- `quote` → `OrderDesk.quote(lines)`。下单前预览，不创建订单、不预留库存、不写任何文件。`lines` 为非空列表，每行含 `sku`（去除首尾空白后非空字符串，区分大小写）和正整数 `quantity`（不接受布尔值），行内额外字段忽略；清单非列表或为空、行不是对象、缺少必要字段、sku 非法、数量为零/负数/非整数、商品不存在均抛出 `ValueError`，整次预览不返回部分结果。清单中只要包含一个暂停销售商品（含未纳管商品）即整次抛出 `ValueError`。相同 sku 合并数量，商品行按 sku 升序；返回仅含 `lines`、`total_cents`、`can_place`，每行仅含 `sku`、`quantity`、`unit_price_cents`、`subtotal_cents`、`available`、`shortfall`。单价只取当前目录，小计为合并数量乘单价，缺货商品和零价商品都保留。纳管商品 `available` 为在库量减预留量，`shortfall` 为需求超过可用量的部分（未超过为零）；未纳管商品（含无库存字段的旧数据）`available` 为 `null`、`shortfall` 为零。所有行缺口为零时 `can_place` 为 `true`。预览不锁定价格或库存，随后交给 `place` 时仍按当时数据校验和预留。恢复启用后，`quote`、`place`、`amend` 恢复既有规则。
- `get` → `OrderDesk.get(...)`。参数名见 `core.py` 的公开方法签名。
- `save-cart` → `OrderDesk.save_cart(cart_id, lines)`。保存可稍后结算的购物清单，关闭工作台后仍可继续处理。`cart_id` 为去除首尾空白后的非空字符串（区分大小写），与订单编号互不占用；新编号创建清单，同一编号再次保存完整替换。`lines` 为非空列表，每行含 `sku`（规则同 `quote`）和正整数 `quantity`（不接受布尔值），行内额外字段忽略；重复 SKU 合并数量，商品行按 SKU 升序。返回仅含 `cart_id`、`lines`，每行仅含 `sku`、`quantity`。清单非列表或为空、行非对象或缺少 `sku`/`quantity`、SKU 非法、数量非正整数或为布尔值、商品不存在、清单编号非法均抛出 `ValueError`，失败不创建或改写清单。暂停销售和库存不足的商品可以保存；保存不记录价格、不预留库存、不创建订单或历史。清单随业务数据保存在 `root/data.json`，重新打开同一 root 后未结算清单仍可查询。
- `cart` → `OrderDesk.get_cart(cart_id)`。查询已保存的清单，返回仅含 `cart_id`、`lines`（每行仅含 `sku`、`quantity`）。`cart_id` 非法或清单不存在均抛出 `ValueError`；查询不创建目录或文件。旧数据缺少清单时视为空集合，不补造记录。
- `checkout-cart` → `OrderDesk.checkout_cart(cart_id, order_id)`。把已保存清单结算为订单：使用结算当时的目录与库存，遵守 `place` 的商品校验、成交金额和预留规则，成功返回与 `place` 相同的完整订单结果，新增一条 `action` 为 `place` 的历史事件，并同时移除该清单（重新打开后已结算清单不会恢复）。未知清单、编号非法、订单编号已存在、暂停商品或库存不足均抛出 `ValueError`，清单、订单、库存与历史不变。未纳管商品结算仍不限制数量且不产生预留。
- `checkout-cart-part` → `OrderDesk.checkout_cart_part(cart_id, order_id, lines)`。部分结算：只为选定的商品及数量创建新订单，清单中剩余内容继续保留。`cart_id`、`order_id` 为去除首尾空白后的非空字符串（区分大小写），清单与订单编号各自独立；`lines` 为非空列表，每行含 `sku`（规则同 `quote`）和正整数 `quantity`（不接受布尔值），行内额外字段忽略；重复 SKU 合并数量后，每项都必须属于该清单且不超过清单当前数量。成功结果只含 `order` 和 `cart`：`order` 沿用既有完整订单结构，仅含本次所选商品，重复 SKU 合并后按 SKU 升序，成交价取提交时目录、金额用整数分，纳管商品仅为本次数量预留当前可用库存且在库量不变，未纳管商品不限制库存且不自动纳管；`cart` 沿用现有清单结构，扣减所选数量并按 SKU 升序、零数量行移除，全部被选走时删除清单并返回 `null`（随后查询该编号抛出 `ValueError`）。未选商品即使停售、缺货或目录缺失也不阻止本次结算、剩余数量不变。编号非法、未知清单、订单编号已存在、`lines` 非列表或为空、行非对象或缺字段、SKU 非法、数量非法、所选商品不属于清单或超量、当前目录缺少所选商品、所选商品停售或纳管库存不足均抛出 `ValueError`；任何一项失败都不改写文件、不创建目录、不消耗序号，也不保留部分变更。订单与库存历史沿用 `place` 规则，不新增清单事件；成功时订单、清单和历史同次保存到 `root/data.json`，重开结果一致。旧数据缺少清单集合时按空处理。
- `checkout-cart-batch` → `OrderDesk.checkout_cart_batch(checkouts)`。整批购物清单结算：一个 `checkouts` 请求把多个已保存清单各自完整结算为指定的新订单，全部成功或全部拒绝。`checkouts` 为非空列表，每项是含 `cart_id`、`order_id` 的对象（行内额外字段忽略）；两个编号均为去除首尾空白后的非空字符串，区分大小写，清单编号空间与订单编号空间相互独立、可取相同文本，但同批内归一化后的清单编号各自不能重复、订单编号各自不能重复。列表类型错误或为空、项目非对象、缺少字段、编号非字符串或为空白、归一化后编号重复、清单不存在或目标订单编号已占用均使整次抛出 `ValueError`。每笔订单沿用单笔完整结算的商品行及计价语义：成交价取提交时目录、金额用整数分、零价商品保留；任一所选清单含当前目录不存在或暂停销售的商品时整批抛出 `ValueError`。已纳管商品使用在库量减全部既有预留（含本批之外订单的预留）后的可用量，多个清单对同一商品的合计需求不得超过这份余量：例如两个清单各需三件、可用五件时整批拒绝且两个清单保留（不跳过缺货清单），可用六件时创建两单并预留六件、在库量不变；任一商品不足即整批抛出 `ValueError`。未纳管商品不限制数量、不自动纳管，也不产生预留；旧商品缺少 `enabled` 时仍视为启用。成功返回按订单编号升序的完整订单数组，每项结构同单笔结算，所选清单全部移除（随后查询这些清单抛出 `ValueError`），未选清单、已有订单及其预留不变。订单、清单移除、预留和历史同次保存到 `root/data.json`，重新打开结果一致；订单与库存历史沿用 `place` 规则，共用商品的库存事件按输入顺序接续（后一笔 `before` 接续前一笔 `after`），旧快照和已有 `complete` 不变，无历史的新订单从 1 开始且 `complete` 为 `true`，不新增批次或清单事件。任一校验失败（包括末项失败）都不改写文件、不创建目录、不消耗历史序号或保留前项变更。旧数据缺少清单集合时按空处理。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；整批一致性仅限一次 `checkouts` 请求。
- `cancel` → `OrderDesk.cancel(...)`。取消只释放该订单实际预留的数量，在库量不变。
- `ship` → `OrderDesk.ship(order_id, carrier, tracking_no)`。一次性整单发货：状态改为 `shipped`，订单新增仅含 `carrier`、`tracking_no`（均去除首尾空白）的 `shipment`。按该订单实际预留的数量同时扣减在库量与预留量，可用量不变；未纳管商品、下单后才纳管的商品及无预留记录的旧订单不扣库存。订单不存在、已取消或已发货均报错，重复发货不覆盖记录或再次扣减。
- `ship-batch` → `OrderDesk.ship_batch(shipments)`。整批发货登记：一个 `shipments` 请求中的订单全部成功或全部拒绝。`shipments` 为非空列表，每项是含 `order_id`、`carrier`、`tracking_no` 的对象（行内额外字段忽略），三者均为去除首尾空白后的非空字符串，订单编号区分大小写，归一化后重复编号拒绝。列表为空或类型不符、项目不是对象、缺少必要字段、字段非法、编号重复、订单未知或状态不是 `placed`（已取消或已发货）均抛出 `ValueError`，整批不返回部分结果：数据文件内容、库存、预留与历史均不变，也不创建原本不存在的目录。成功时返回按订单编号升序排列的完整订单数组，每项与 `ship` 成功结果相同（状态为 `shipped`，`shipment` 采用去除首尾空白后的值）；每笔订单只扣减其实际预留对应的在库量与预留量，可用量不变，未在本批中的订单预留保留。未纳管商品、下单后才纳管但没有实际预留的商品及无预留记录的旧订单均不扣库存；暂停销售商品仍可发货，订单商品行、金额与重复 SKU 的原有排列保留；不同订单允许使用相同运单号。每笔订单追加一条 `action` 为 `ship`、`result` 为该笔返回快照的历史事件，序号接续该订单原历史，旧事件与已有 `complete` 不变，无历史的旧订单从 1 开始且 `complete` 为 `false`；订单与各自历史同次保存到 `root/data.json`，重新打开结果一致。批量发货后的订单仍按原规则登记退货。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；整批一致性只限单个 `shipments` 请求。
- `confirm-delivery` → `OrderDesk.confirm_delivery(order_id, recipient, delivered_on)`。离线签收确认：把 `shipped` 订单改为 `delivered`，订单新增仅含 `recipient`、`delivered_on`（均去除首尾空白）的 `delivery`。签收日期由调用方提供，不读取系统时间，必须是真实有效的 `YYYY-MM-DD` 日历日期，非字符串、空白值、其他格式或 `2026-02-29` 之类非法日期均抛出 `ValueError`；订单编号与签收人须为去除首尾空白后的非空字符串，编号区分大小写。输入不合法、订单未知或状态不是 `shipped` 均抛出 `ValueError`，失败不改写数据、不消耗历史序号；重复签收即使内容相同也拒绝，不覆盖记录。签收不改变商品行、金额、shipment、库存、预留和已有退货，也不追加库存事件；已有退货不阻止签收。成功返回完整订单，`get`、`list` 与 `history` 显示 `delivered` 状态并保留 `delivery`。签收追加一条 `action` 为 `confirm-delivery`、`result` 为完整返回订单快照的历史事件，序号接续该订单原历史，旧事件与已有 `complete` 不变；签收与历史同次保存到 `root/data.json`，重新打开结果一致。旧 shipped 订单缺少 shipment 或历史时仍可签收，不补造发货信息；无历史的旧订单新事件从 1 开始且 `complete` 为 `false`。签收订单不能再改商品、取消或发货，也不纳入拣货汇总，相关入口均抛出 `ValueError`，批量发货仍整批拒绝；签收后的退货登记、入库、撤销和 return-worklist 继续按已发货订单的原规则办理，订单保持 `delivered`。
- `confirm-shipment-delivery` → `OrderDesk.confirm_shipment_delivery(carrier, tracking_no, recipient, delivered_on)`。按同一运单统一签收：一次请求把当前关联该承运商与运单号的全部 `shipped` 订单改为 `delivered`，在逐单 `confirm-delivery` 之外新增，不影响其他入口的既有行为。`carrier`、`tracking_no`、`recipient` 均须为去除首尾空白后的非空字符串（区分大小写），`delivered_on` 沿用 `confirm-delivery` 的真实 `YYYY-MM-DD` 日历日期校验，日期由调用方提供、不读取系统时间；任一输入非法均抛出 `ValueError`。关联范围沿用 `shipment-orders` 的当前发货信息匹配规则：只匹配订单当前 shipment 中的同名字段（两侧去空白后精确匹配），不匹配历史 `ship`、`correct-shipment` 快照，只纳入当前状态为 `shipped` 或 `delivered` 的订单，shipment 缺失、非对象或必要字段缺失、非字符串、只有空白的订单直接跳过；合法组合没有任何匹配订单时抛出 `ValueError`。一次请求将全部匹配的 `shipped` 订单改为 `delivered`，`delivery` 仅保存规范化后的 `recipient` 与 `delivered_on`；已签收的匹配订单两项规范化后与请求一致时保留原记录，任一项不一致，或 `delivery` 不是对象、缺字段、文本或日期非法时整次抛出 `ValueError`，其他订单也不签收。成功结果仅含 `carrier`、`tracking_no`、`orders`，前两项为规范化后的输入，`orders` 按订单编号升序返回全部匹配订单（含本次新签收与原本已签收的）的完整结果，结构沿用 `get`。全部匹配订单已按相同信息签收时仍返回成功结果，但不写文件、不追加事件；混合状态时只为尚未签收的订单新增记录。有新增签收时，订单与历史同次保存到 `root/data.json`，重新打开后 `get`、`history` 与履约待办（`order-worklist` 的 `deliver` 任务）反映新状态；每笔新签收订单追加一条 `action` 为 `confirm-delivery`、`result` 为完整订单快照的历史事件，序号接续该订单原历史，旧事件与已有 `complete` 不变，无历史的旧订单从 1 开始且 `complete` 为 `false`，不补造过去。商品行、金额、shipment、库存、预留、购物清单及已有退货均保留，退货不阻止签收，也不新增库存事件。任何失败都不改写文件、不创建目录或消耗序号；逐单 `confirm-delivery` 仍拒绝重复提交（包括对本命令已签收的订单）。命令沿用成功输出 JSON 并退出 0、失败向标准错误输出 error 对象并退出 2 的约定，外层 JSON 数组逐项独立执行，前项成功不因后项失败回滚。
- `correct-shipment` → `OrderDesk.correct_shipment(order_id, expected_shipment, shipment)`。带原信息核对的发货记录更正：仅 `shipped`、`delivered` 订单可更正，已有退货不阻止操作；状态、商品行顺序、单价、金额、签收（`delivery`）与退货记录均保留，库存及各订单预留不变，不新增库存历史，也不改变订单状态。`order_id` 及两个信息对象内的 `carrier`、`tracking_no` 均为去除首尾空白后的非空字符串（区分大小写），两个信息对象必须是对象且行内额外字段忽略；编号非字符串或为空白、信息参数非对象或缺少必要文本均抛出 `ValueError`。先核对原信息：`expected_shipment` 两项必须与当前记录的 shipment 完全一致（区分大小写）才允许替换，当前 shipment 缺失或其中必要文本无效同样抛出 `ValueError`，不被静默覆盖；允许只改其中一项，不要求运单号跨订单唯一。订单未知或状态不符（含 `placed`、`cancelled`）、原信息核对失败（即使目标信息恰好等于当前记录）均抛出 `ValueError`，失败不改写数据、不创建目录、不追加事件或消耗序号。成功结果仅含 `order_id`、`before`、`after`，前后快照仅含 `carrier`、`tracking_no`，分别反映更正前后的发货信息；更正后 `get` 与 `list` 展示最新 shipment，旧历史快照保持原样。有实际变化时，更正与一条 `action` 为 `correct-shipment`、`result` 为返回快照的订单历史事件同次保存到 `root/data.json`，重新打开结果一致：序号接续该订单原历史，旧事件与已有 `complete` 不变，无历史的旧订单事件从 1 开始且 `complete` 为 `false`，不补造过去。原信息核对通过但目标与当前完全一致时仍返回结果，只是不写文件、不追加事件或消耗序号。原 `ship` 与 `ship-batch` 仍拒绝重复发货；命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚。
- `quote-return` → `OrderDesk.quote_return(order_id, lines)`。退货登记前的只读金额预览：按订单保存的成交价核算拟退商品金额并判断可退额度，不生成退货记录、不执行退款、不写任何文件。仅 `shipped` 与 `delivered` 订单可预览；停售、缺货、未纳管或当前目录缺少商品均不阻止原订单商品预览，既有登记和入库规则保持不变。`order_id` 与 SKU 均为去除首尾空白后的非空字符串（区分大小写）；`lines` 为非空列表，每行含 `sku` 和正整数 `quantity`（不接受布尔值），行内额外字段忽略，重复 SKU 合并数量。结果仅含 `order_id`、`lines`、`total_cents`、`can_record`，商品行按 SKU 升序且仅覆盖本次请求，每行仅含 `sku`、`quantity`、`unit_price_cents`、`subtotal_cents`、`remaining`。单价取订单保存的非负整数成交单价（不接受布尔值，零价有效），不以目录价格替代；小计为请求量乘单价，总额为各小计之和，金额使用整数分。`remaining` 为原订单合并订购量减当前有效退货登记量：已入库登记仍占额度，撤销记录不占额度，更正记录按最新数量计算；旧数据缺少退货记录视为未退，不补造历史。所有请求量不超过各自 `remaining` 时 `can_record` 为 `true`，否则为 `false`；超量仍返回完整请求金额，不截减数量。编号非法或未知、订单状态不符、清单类型错误或为空、行非对象或缺字段、SKU 非法或不属原订单、数量非法，以及请求商品的成交单价缺失、非法或同一 SKU 原订单各行单价不一致，均整次抛出 `ValueError`，不返回部分结果。成功或失败均不创建目录或改写文件，不改变库存、预留、订单、清单、凭据、历史及序号；相同数据重复查询或重新打开结果一致，预览不占用额度，后续登记仍按当时数据校验。
- `record-return` → `OrderDesk.record_return(order_id, return_id, lines)`。分次退货登记，接受 `shipped` 与 `delivered` 订单（签收保持 delivered 状态）；只登记退货，不退款、不回补库存，订单状态、金额、商品行、shipment/delivery 与其他订单预留量均不变。退货编号在整个 root 内唯一，重复提交（即使内容相同）拒绝且不覆盖。订单编号、退货编号与 SKU 均须为非空字符串（去除首尾空白，区分大小写）；`lines` 为非空列表，每行含 `sku` 和正整数 `quantity`（布尔值不接受）。本次输入及原订单中的重复 SKU 分别合并数量，累计成功退货量加本次数量不得超过原订量，任一 SKU 超量或不属于原订单则整次登记拒绝。成功返回仅含 `order_id`、`return_id`、`lines` 的记录，商品行按 sku 升序，每项仅含 `sku`、`quantity`。
- `returns` → `OrderDesk.get_returns(order_id)`。返回 `{order_id, records, remaining}`：`records` 按 return_id 升序，`remaining` 按 sku 升序覆盖原订单全部商品，数量为原订量减累计退货量，零也保留。已有订单均可查询，无退货记录时 `records` 为空；查询不写文件。
- `receive-return` → `OrderDesk.receive_return(return_id)`。整笔退货入库，与分次退货登记相互独立：登记本身仍不回补库存，入库不要求逐个商品行，数量取该退货编号登记记录中的全部商品行。一次性把各行数量加回当前在库量，预留量及各订单预留记录不变，可用量相应增加。商品必须在当前目录中存在且已纳管（至少成功补货一次）；入库不自动纳管商品，发货后才纳管的商品按当前库存处理。任一商品未知或未纳管则整次入库拒绝。`return_id` 为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号、未知退货、已撤销编号、所属订单不存在或既非 `shipped` 也非 `delivered` 均抛出 `ValueError`。同一 root 内每个退货编号只能成功入库一次，重复提交拒绝且不覆盖原记录或再次加库存；失败不改写数据、不新增历史或消耗序号。成功返回仅含 `order_id`、`return_id`、`lines`，商品行按 sku 升序，每行仅含 `sku`、`quantity`、`before`、`after`；`quantity` 取原退货记录数量（同 sku 合并），`before` 与 `after` 沿用 stock 的完整库存结构（`{sku, on_hand, reserved, available}`）。入库不改变订单状态、金额、商品行、shipment 及退货登记记录。已成功入库的退货不可撤销。
- `receive-return-batch` → `OrderDesk.receive_return_batch(return_ids)`。整批退货入库：一个 `return_ids` 请求中的退货全部成功或全部拒绝。`return_ids` 为非空列表，每个编号为去除首尾空白后的非空字符串（区分大小写），归一化后重复编号拒绝；列表为空或类型不符、编号非法、退货未知、已撤销或已入库、所属订单不存在或既非 `shipped` 也非 `delivered` 均抛出 `ValueError`。每笔退货仍按 `receive-return` 规则整笔入库：任一商品不存在或未纳管同样抛出 `ValueError`，暂停销售不阻止入库，发货后才纳管的商品按当前库存处理。任一项失败（包括末项）就拒绝整批：不改变文件、库存、凭据和历史，不创建目录或消耗序号。成功时按输入顺序逐笔增加在库量，预留量及各订单预留不变，可用量等量增加；共用商品的后一笔 `before` 接续前一笔 `after`。返回按 `return_id` 升序的数组，每项沿用 `receive-return` 的完整凭据结构和商品行排序，并可由 `return-receipt` 查询。每笔在对应订单历史追加 `action` 为 `receive-return`、`result` 为该笔凭据的事件，各商品按既有库存历史格式记录同名事件，`reference_id` 为退货编号；同一订单或共用商品的事件遵循输入顺序，序号各自接续，旧快照和已有 `complete` 不变，无历史的旧数据从 1 开始且 `complete` 为 `false`，无凭据的旧登记视为未入库。库存、凭据和历史同次保存到 `root/data.json`，重新打开一致，后续操作不改写快照。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；整批一致性只限单个 `return_ids` 请求。成功入库后 `return-worklist` 显示 `received`，重复入库及撤销均沿用现有规则抛出 `ValueError`；不增加退款或部分入库。
- `cancel-return` → `OrderDesk.cancel_return(return_id)`。撤销一笔尚未入库的整笔退货登记，不接受部分撤销，且不处理已入库登记（已入库须用 `cancel-received-return` 整笔冲销）：该笔从 `get_returns` 及 `returns` 的 `records` 中移除，`remaining` 按仍有效的登记重新计算（覆盖原订单全部商品并保留零数量行），其他退货登记不受影响。撤销仅释放可退数量，不增减在库量或预留量，不改变订单状态、金额、商品行与 shipment，也不影响其他订单。成功返回原登记的 `order_id`、`return_id`、`lines`，商品行仅含 `sku` 和 `quantity`，重复 SKU 合并并按 SKU 升序。`return_id` 为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号、未知退货、重复撤销、已入库以及所属订单不存在或既非 `shipped` 也非 `delivered` 均抛出 `ValueError`；`receive-return` 对已撤销编号同样抛出 `ValueError`。失败不改写数据、不新增事件或消耗序号。撤销后原 `return_id` 仍在整个 root 内占用，`record-return` 即使换一笔订单也抛出 `ValueError` 拒绝重用；后续可用新编号登记释放出的可退数量。撤销记录与历史事件随业务变更同次保存到 `root/data.json`，重新打开后结果一致。
- `cancel-received-return` → `OrderDesk.cancel_received_return(return_id)`。在整笔退货入库之外新增的整笔冲销：把原入库凭据数量从各商品**当前**在库量中整笔扣减（保留入库之后的补货、发货和盘点等变动，例如入库三件后又发货两件，冲销只扣回三件而不重放发货），可用量等量减少，预留量及各订单实际预留归属均不变；只处理未撤销、有入库凭据且所属订单为 `shipped` 或 `delivered` 的退货，`cancel-return` 仍拒绝已入库登记。`return_id` 为去除首尾空白后的非空字符串（区分大小写），非字符串或空白编号、未知退货、已撤销、未入库、所属订单缺失或状态不符均抛出 `ValueError`。凭据涉及的任一商品在当前目录缺失或未纳管（含入库后库存记录丢失的旧数据），或任一商品扣减后在库量为负或低于当前预留量，同样整次抛出 `ValueError`：不改写文件、不创建目录、不改变库存、退货、凭据、历史或序号；重复冲销（编号仍在 active 记录之外、凭据已被冲销）也抛出 `ValueError`。停售不阻止操作，订单状态、商品行、金额、shipment/delivery 均保留，不退款。成功后该退货从有效登记移入撤销集合、变为 `cancelled` 并释放可退数量（`returns` 与 `quote-return` 不再计该笔额度），编号在同一 root 内继续占用，不能再登记、更正或再次入库；`return-receipt` 仍返回原入库快照。成功返回沿用 `receive-return` 的凭据结构，仅含 `order_id`、`return_id`、`lines`，商品行按 SKU 升序合并，每行仅含 `sku`、`quantity`、`before`、`after`：`quantity` 为冲销量（取原凭据数量），`before`、`after` 为冲销前后完整 stock 快照（`{sku, on_hand, reserved, available}`）。变更与历史同次保存到 `root/data.json`，重新打开结果一致：订单追加一条 `action` 为 `cancel-received-return`、`result` 为返回凭据的历史事件，各商品按既有库存历史格式记录同名事件，`reference_id` 为退货编号，序号各自接续，旧快照及已有 `complete` 保留，无历史的旧数据从 1 开始且 `complete` 为 `false`，不补造历史。缺少凭据的旧登记仍按未入库处理，其他公开入口保留既有行为：`return-worklist` 在 `cancelled` 阶段展示该笔（其余阶段不展示），订单及运单的履约数量和金额汇总（`order-progress`、`shipment-orders`、`fulfillment-summary`）排除该笔回库量，净发出量与净金额相应增加，`order-worklist` 不新增入库任务。命令沿用成功 JSON 输出并退出 0、失败向标准错误输出 error 对象并退出 2、外层 JSON 数组逐项独立执行的约定。
- `amend-return` → `OrderDesk.amend_return(return_id, expected_lines, lines)`。待入库退货的整笔更正：退货编号与所属订单不变，原清单核对一致后完整替换商品行，允许增减数量和增删原订单商品。`return_id` 为去除首尾空白后的非空字符串（区分大小写）；`expected_lines` 与 `lines` 均为非空列表，每行含 `sku`（去除首尾空白后非空、区分大小写）和正整数 `quantity`（布尔值不接受），行内额外字段忽略；输入及当前登记的重复 SKU 分别合并数量，按 SKU 升序比较，行序不影响核对。仅所属订单为 `shipped` 或 `delivered` 的待入库登记可更正；暂停销售、未纳管或目录缺少商品不阻止原订单商品更正。以原订单合并订购量为上限：新量加同单其他有效登记（含已入库登记）不得超量，本次旧登记和已撤销登记不占额度（订购五件、其他登记一件、本次原有三件时可改为四件，五件拒绝）。编号非法、退货未知、已撤销或已入库、所属订单缺失或状态不符、清单为空或类型错误、行非对象、缺字段、SKU 或数量非法、原内容不符、新商品不属原订单或超量均抛出 `ValueError`，整笔不写文件、不创建目录或消耗序号；目标与当前相同也先核对原内容。成功仅返回 `order_id`、`return_id`、`before`、`after`，前后两项为归并排序后的清单，每行仅含 `sku`、`quantity`。有实际变化时，登记与 `action` 为 `amend-return`、`result` 为返回快照的一条订单历史事件同次保存到 `root/data.json`，序号接续，旧快照和 `complete` 不变，无历史的旧订单从 1 开始且 `complete` 为 `false`，无入库凭据的旧登记按待入库处理；内容未变仍成功，但不写文件或追加事件。重新打开后，`returns` 的可退数量和 `return-worklist` 显示新登记，后续撤销及单笔、批量入库使用新数量；库存、预留、成交内容、发货签收及其他登记不变。
- `return-receipt` → `OrderDesk.get_return_receipt(return_id)`。返回入库时的完整快照，仅含 `order_id`、`return_id`、`lines`；后续补货、下单、取消、发货、盘点或再次入库均不改写该快照，重新打开同一 root 结果一致。`return_id` 须为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号、未知退货及尚未入库均抛出 `ValueError`；查询不创建目录或写文件。无入库记录的旧数据视为尚未入库，不补造记录。
- `return-worklist` → `OrderDesk.return_worklist(stage="pending", order_id=None)`。跨订单的只读退货处理清单，不影响登记、入库、撤销及其他公开入口的既有行为。`stage` 去除首尾空白后只接受 `pending`、`received`、`cancelled`、`all`（非字符串或其他值均抛出 `ValueError`），`all` 表示查询全部阶段；`order_id` 为 `null` 时查询整个 root，否则须为去除首尾空白后区分大小写的非空字符串，未知订单抛出 `ValueError`，已知订单没有匹配登记时返回空数组。有效登记有入库凭据时为 `received`，没有时为 `pending`（无入库凭据的旧数据视为待入库）；撤销登记为 `cancelled`，仍可查询；缺少退货或撤销记录视为空集合，不从历史补造登记。结果为按 `return_id` 升序的数组，每项仅含 `order_id`、`return_id`、`stage`、`lines`、`can_receive`、`blockers`；`lines` 取原登记数量，重复 SKU 合并并按 SKU 升序，每行仅含 `sku`、`quantity`。仅 `pending` 登记检查当前目录和库存：商品不存在时阻碍原因是 `unknown-product`，商品存在但未纳管（含无库存记录的旧数据）时为 `unmanaged`；`blockers` 每项仅含 `sku`、`reason`，按 SKU 升序。`pending` 且无阻碍时 `can_receive` 为 `true`，其余情况（含 `received`、`cancelled` 及有阻碍的 `pending`）为 `false`；非 `pending` 登记的 `blockers` 为 `[]`。暂停销售不阻止入库，不产生阻碍。清单所含登记的订单不存在或既非 `shipped` 也非 `delivered` 时，整次查询抛出 `ValueError`，不返回部分结果。登记、入库、撤销或补货后再次查询反映最新阶段与入库阻碍；查询成功或失败均不创建目录或写文件，不改变库存、订单、购物清单、历史及序号；业务数据未变时重新打开相同 root 结果一致。
- `history` → `OrderDesk.history(order_id)`。按实际发生顺序返回订单过程，仅含 `order_id`、`status`、`complete`、`events`：`status` 为订单当前状态；`complete` 表示历史是否包含真实创建事件。`events` 按成功操作先后排列，每项仅含 `sequence`、`action`、`result`；`sequence` 在每个订单内从 1 连续递增，`action` 为 `place`、`amend`、`reserve-order`、`transfer-reservation`、`release-reservation`、`cancel`、`ship`、`confirm-delivery`、`correct-shipment`、`record-return`、`receive-return`、`cancel-return`、`amend-return`、`cancel-received-return`，`result` 保存对应公开方法成功返回内容的快照（创建保留成交商品行与金额，发货保留 shipment，签收保留含 delivery 的完整订单，发货更正仅保留前后 shipment 快照，退货保留归并后的记录，入库保留各行入库前后库存快照，撤销保留原登记的归并记录，退货更正保留前后归并清单，已入库冲销保留各行冲销前后库存快照），后续操作不改写旧快照。操作失败不新增事件、不消耗序号；退货编号即使逆序提交，历史仍按登记顺序显示。历史随业务数据保存在 `root/data.json`，与业务变更同次写入，重新打开同一 root 结果一致。无历史数据的旧订单查询时 `events` 为空、`complete` 为 `false`，不依据状态或已有退货记录补造；这类订单随后成功取消、发货或登记退货时从 1 开始记录新事件，`complete` 仍为 `false`，新创建订单为 `true`。`order_id` 须为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号及未知订单均抛出 `ValueError`；查询不创建目录或写文件。
- `order-progress` → `OrderDesk.order_progress(order_id)`。单笔订单履约数量的只读总览，把备货缺口与退货回库后的净发出量放在一起，不影响 `get`、`history`、`returns` 及其他公开入口的既有行为。已有订单（任意状态）均可查询；`order_id` 须为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号及未知订单均抛出 `ValueError`。结果仅含 `order`、`history`、`lines`：前两项分别与现有 `get`、`history` 的完整结果一致。`lines` 合并当前订单的重复 SKU，按 SKU 升序覆盖订单当前全部商品（零值保留），每行仅含 `sku`、`ordered`、`reserved`、`needed`、`shipped`、`pending`、`received`、`remaining`、`net`，分别表示商品、订购量、本单预留、仍需预留、发出量、待回库量、已回库量、剩余可退量、净发出量。`placed` 订单的纳管商品（以库存记录为准）以本单实际预留计数（缺少预留记录为零），`needed` 为订购量减预留量与零取较大值，不抵扣可用库存；未纳管商品及其他状态的订单预留两项均为零。`shipped`、`delivered` 订单的 `shipped` 为订购量，其余状态为零，不按库存扣减推算。本单有效退货登记有入库凭据时数量计入 `received`，否则计入 `pending`：取登记最新清单（更正后的数量），撤销记录不计入，旧数据缺少预留、退货或入库集合时按空处理，绝不从历史推算数量。`remaining` 仅在 `shipped`、`delivered` 时为订购量减退货两项（待回库与已回库），其余状态为零；`net` 恒为发出量减已回库量（例如发出五件、两件待回库、一件已回库时，剩余可退量为二、净发出量为四）。停售或目录缺少商品不阻止查询，纳管一律以库存记录为准；缺发货签收信息或历史也不补造。预留与退货处理（登记、更正、撤销、入库）后再次查询反映最新数量。查询不创建目录、写文件或消耗历史序号，数据未变时重复查询及重新打开结果一致。
- `shipment-orders` → `OrderDesk.shipment_orders(carrier, tracking_no)`。按承运商与运单号组合查找关联订单的只读查询，在按订单编号查看履约过程之外新增，不影响 `ship`、`ship-batch`、`confirm-delivery`、`correct-shipment`、退货与其他查询入口的既有行为。`carrier`、`tracking_no` 均须为去除首尾空白后的非空字符串（区分大小写），非字符串或去空白后为空均抛出 `ValueError`。只匹配订单**当前** shipment 中的同名字段：两侧都去除首尾空白后精确匹配并区分大小写，绝不匹配历史中 `ship`、`correct-shipment` 事件保存的旧发货信息；只纳入当前状态为 `shipped` 或 `delivered` 的订单，不要求运单号唯一，同一运单关联多笔订单时全部返回。旧订单缺少 `shipment`、该字段不是对象，或其中 `carrier`、`tracking_no` 缺失、非字符串或只有空白时直接跳过，不补造发货信息、不报错；`placed`、`cancelled` 订单即使带 shipment 形状的字段也不纳入。合法组合没有匹配时仍返回查询组合，`orders`、`lines` 均为空数组。缺少订单、历史、退货及入库集合时沿用既有空集合语义，停售、未纳管或当前目录已缺少商品都不阻止查询。成功结果仅含 `carrier`、`tracking_no`、`orders`、`lines`，前两项为规范化（去首尾空白）后的输入；`orders` 按订单编号升序，每项与该订单的 `order-progress` 完整结果完全一致（含 `order`、`history`、`lines`）。`lines` 合并全部匹配订单当前商品中的重复 SKU（并集），按 SKU 升序，每行仅含 `sku`、`shipped`、`pending`、`received`、`remaining`、`net`，五个数量分别为各匹配订单 order-progress 同名字段之和，零值行保留：已撤销退货不计数，更正登记按最新数量，待入库与已入库按现有凭据口径区分，发出量取订购量而不按库存扣减推算，`net` 只扣已回库量（例如两单合计发出八件，其中两件待回库、一件已回库时，`remaining` 为五、`net` 为七）。发货信息更正后，订单转入新承运商/运单号组合的结果，原组合结果不再包含它。查询成功或失败均不创建目录、不写文件、不改变业务状态或消耗历史序号，数据不变时重复查询及重新打开结果一致。
- `fulfillment-summary` → `OrderDesk.fulfillment_summary()`。整个 root 的只读履约金额汇总，与单笔订单及运单数量查询并列，不接收业务参数，不影响其他公开入口的既有行为。结果仅含 `order_count`、`lines`、`totals`：`order_count` 只计当前状态为 `shipped` 或 `delivered` 的订单，其余状态订单与购物清单均不计入。`lines` 按 SKU 升序归并全部入选订单的商品，每行仅含 `sku`、`shipped`、`pending`、`received`、`net` 以及 `shipped_cents`、`pending_cents`、`received_cents`、`net_cents`：发出量等于各入选订单订购量之和，绝不从库存扣减推算；有效退货登记按登记最新清单（更正后的数量）计数，有入库凭据的数量计入 `received`，其余计入 `pending`，撤销登记不计入；`net` 等于 `shipped` 减 `received`，待回库不扣净发出量。四个金额先把每笔订单的对应数量乘以该订单保存的 `unit_price_cents`，再跨订单求和，均为整数分，绝不取目录现价；不同订单允许同一 SKU 成交价不同，订单内重复 SKU 先合并数量再计价；零价商品与净量为零的行都保留。金额仅表示履约口径，不执行收款或退款。任一纳入订单的任一行缺少成交单价、单价为负数、非整数或布尔值，或同一订单同一 SKU 各行单价不一致时，整次抛出 `ValueError`，不返回部分结果；商品停售、未纳管或当前目录缺失都不阻止汇总。旧数据缺少订单、退货或入库集合时按空处理，不从历史补造；无入选订单时 `order_count` 为零、`lines` 为空、`totals` 各项为零。`totals` 仅含行内八个数值字段，分别为各行对应值之和。查询成功或失败均不创建目录、改写文件或消耗序号，数据不变时重复查询及重新打开结果一致。
- `order-worklist` → `OrderDesk.order_worklist(stage="open")`。跨订单的只读履约待办查询，直接找出仍需补齐预留、发货、确认签收或退货入库的订单，不影响其他公开入口的既有行为。`stage` 去除首尾空白后只接受 `open`、`all`、`reserve`、`ship`、`deliver`、`receive-return`（非字符串、空白或其他值均抛出 `ValueError`）：默认 `open` 只选有待办的订单，`all` 选全部订单（无待办的订单带空 `tasks`），其余值选包含对应待办的订单。待办一律以当前状态为准：`placed` 订单任一纳管商品（以库存记录为准）的 `needed` 大于零时列 `reserve`，否则列 `ship`；`needed` 沿用 `order-progress` 的实际预留口径（订购量减本单实际预留，不抵扣当前可用量），未纳管商品不产生补齐待办。`shipped` 订单列 `deliver`；`shipped` 或 `delivered` 订单存在有效且未入库的退货登记时还列 `receive-return`，商品停售、目录缺失或未纳管也保留该待办；已撤销或已入库登记不产生该待办，更正登记按最新内容判断。`cancelled` 订单无待办，`delivered` 且没有待入库退货也无待办；等待签收且有待入库退货的订单同时出现在 `deliver` 与 `receive-return` 两种筛选中，每次结果只出现一次。结果为按订单编号升序的数组，每项仅含 `order_id`、`tasks`、`progress`；`tasks` 按 `reserve`、`ship`、`deliver`、`receive-return` 固定顺序排列，无待办时为空数组；`progress` 与该单 `order-progress` 的完整结果完全一致。没有匹配订单或旧数据缺少订单集合时返回 `[]`；缺少预留、历史、退货和入库集合沿用现有空集合语义，不从历史补造记录。业务操作（预留、发货、签收、退货登记、更正、撤销、入库）后再次查询反映最新待办，后续操作仍按各入口现有规则校验。查询成功或失败均不创建目录、写文件或消耗序号，数据不变时重复查询及重新打开结果一致；命令沿用现有 JSON 输出、错误退出码与外层数组逐项独立执行的约定。
- `count-stock` → `OrderDesk.count_stock(count_id, lines)`。库存盘点登记，用实际清点数量校准已纳管商品的在库量。`count_id` 为去除首尾空白后的非空字符串（区分大小写），在 root 内唯一，重复提交（即使内容相同）拒绝且不覆盖。`lines` 为非空列表，每行含 `sku`（去除首尾空白后非空字符串，区分大小写）和非负整数 `on_hand`（含零，不接受布尔值），行内额外字段忽略；同一盘点中重复 sku 拒绝，不合并数量。每个商品必须存在且已纳管（至少成功补货一次），新在库量不得低于当前预留量；任一商品未知、未纳管或低于预留量则整次盘点拒绝。成功后一次性替换本次全部商品的在库量，预留量及各订单实际预留记录保留，未列出商品的在库量与预留量均不变。返回仅含 `count_id` 和 `lines`，商品行按 sku 升序，每行仅含 `sku`、`before`、`after`、`delta`；`before` 与 `after` 沿用 stock 的完整库存结构（`{sku, on_hand, reserved, available}`），`delta` 为盘点后在库量减盘点前在库量。盘点记录与库存变更同次写入 `root/data.json`。
- `stock-count` → `OrderDesk.get_stock_count(count_id)`。返回登记时的盘点快照，仅含 `count_id` 和 `lines`；后续补货、下单、取消、发货或再次盘点均不改写该快照，重新打开同一 root 结果一致。`count_id` 须为去除首尾空白后的非空字符串（区分大小写），非字符串、空白编号及不存在的编号均抛出 `ValueError`；查询不创建目录或写文件。无盘点记录的旧数据可正常使用，不补造记录。
- `reverse-stock-count` → `OrderDesk.reverse_stock_count(count_id)`。整笔盘点差额撤销：覆盖原盘点全部商品，各商品新在库量等于当前在库量减原盘点 `delta`（即抵消盘点造成的增减，保留之后的业务变动，例如从十件盘为八件后补货五件，撤销把十三件变成十五件），预量及各订单实际预留不变，可用量据此重算。`count_id` 为去除首尾空白后的非空字符串（区分大小写），编号非法或盘点不存在均抛出 `ValueError`；每笔盘点只可撤销一次，重复撤销抛出 `ValueError`，原盘点编号继续占用。商品停售仍可撤销；商品不存在或未纳管、任一新在库量为负或低于当前预留量时整笔抛出 `ValueError`，不保留其他行的变更。成功凭据仅含 `count_id` 和 `lines`，商品行按 sku 升序，每行仅含 `sku`、`delta`、`before`、`after`，分别表示商品、本次反向变化量和撤销前后的 stock 完整快照；零差额行保留，整笔差额为零也登记撤销凭据，但不新增库存事件。凭据与库存变更同次保存到 `root/data.json`；失败不写文件、不建目录或消耗序号。缺少盘点或撤销记录的旧数据按空集合处理，不补造记录。
- `stock-count-reversal` → `OrderDesk.get_stock_count_reversal(count_id)`。返回撤销时保存的同一凭据，仅含 `count_id` 和 `lines`；后续业务不改写凭据或原盘点快照，重新打开同一 root 结果一致。`count_id` 须为去除首尾空白后的非空字符串（区分大小写），编号非法、盘点不存在或尚未撤销均抛出 `ValueError`；查询始终只读，不创建目录或写文件。
- `stock-history` → `OrderDesk.stock_history(sku)`。按商品追溯在库量与预留量的变动，仅返回 `{sku, complete, events}`：`complete` 表示历史是否覆盖首次纳管以来的全部变动。`events` 按成功变动先后排列，`sequence` 在该商品内从 1 连续递增，每项仅含 `sequence`、`action`、`reference_id`、`before`、`after`；`before` 与 `after` 沿用 stock 的完整库存结构（`{sku, on_hand, reserved, available}`）。补货、下单、改单、预留补齐、预留释放、取消、发货、退货入库、已入库退货冲销、盘点和盘点撤销在成功改变在库量或预留量时各记录一条事件，`action` 为对应单笔命令名（`restock`、`place`、`amend`、`reserve-order`、`release-reservation`、`cancel`、`ship`、`receive-return`、`cancel-received-return`、`count-stock`、`reverse-stock-count`），购物清单结算记为 `place`，批量发货记为 `ship`；`reference_id` 在补货时为 `null`，下单、改单、预留补齐、预留释放、取消、发货时为订单编号，退货入库、已入库退货冲销、盘点和盘点撤销时为退货编号或盘点编号。批量发货按请求内订单顺序逐笔记录，共用商品的快照连续衔接；已入库退货冲销的数量恒为正，只要冲销成功（在库量下降）必记事件；改单每个 SKU 仅记录最终净变化，不记录临时释放与预留；同值盘点、净库存不变的改单及没有实际预留的取消或发货均不新增事件，既有业务结果与订单历史照常产生。首次补货从未纳管变为纳管也算变化，其 `before` 为 stock 的未纳管结果；暂停销售不影响记录规则。事件与业务变更同次保存在 `root/data.json`，重新打开结果一致，后续操作不改写旧快照；操作失败不新增事件或消耗序号，整批发货拒绝时也不留下事件。尚未纳管的商品返回 `complete` 为 `true` 的空历史；已纳管但缺少历史的旧商品返回 `complete` 为 `false` 和空事件，后续事件从 1 开始且 `complete` 一直为 `false`，不从已有订单或盘点补造过程。`sku` 去除首尾空白后匹配并区分大小写，非字符串、空白值或未知商品均抛出 `ValueError`；查询不创建目录或写文件。
- `pick-list` → `OrderDesk.pick_list(order_ids)`。只读拣货汇总，合并所选待发货订单的备货数量并保留各订单数量明细，仅供备货参考，不影响 `ship` 及其他公开入口的既有行为。`order_ids` 为非空列表，每项是去除首尾空白后的非空字符串（区分大小写），归一化后重复编号不接受；列表类型不符、编号非法、订单不存在或状态不是 `placed` 时整次查询抛出 `ValueError`，不返回部分汇总。返回仅含 `order_ids`（所选编号升序）和 `lines`（按 sku 升序），每行仅含 `sku`、`quantity`、`reserved`、`available`、`shortfall`、`orders`：`quantity` 为所选订单当前商品行数量合计（订单内重复 SKU 也合并）；`orders` 按 order_id 升序列出包含该商品的订单，每项仅含 `order_id`、`quantity`（该订单合并需求量）、`reserved`（该订单实际预留量）；行级 `reserved` 只合计所选订单的实际预留量，不计入其他订单预留，也不把标称需求当成预留。纳管商品 `available` 与 stock 一致，`shortfall` 为 `quantity - reserved - available` 与零取较大值（可用量为零但自身已足额预留时缺口仍为零）；未纳管商品（含缺少库存记录的旧数据）`available` 为 `null`、`reserved` 和 `shortfall` 为零，商品行仍保留。缺少订单预留记录时实际预留量为零；下单后才纳管的商品按当前可用量计算缺口，不补造预留。暂停销售商品仍参与汇总，`amend` 后再次查询以修改后的数量为准。查询不创建目录或文件，不改变库存、订单、购物清单、历史事件及序号；业务数据未变时重新打开同一 root 结果一致。
- `reservation-plan` → `OrderDesk.reservation_plan(order_ids)`。只读的预留补齐优先预览：按给定订单顺序（输入顺序即优先级，编号去除首尾空白后区分大小写）逐单判断共享库存下哪些订单可以完整补齐，不执行补齐，不影响 `reserve-order`、`pick-list` 及其他公开入口的既有行为。`order_ids` 为非空列表，归一化后重复编号、类型不符、编号非法（非字符串或空白）、未知订单、状态非 `placed` 或任一订单商品不在当前目录中均整次抛出 `ValueError`，不返回部分结果。返回保留输入顺序的数组，每项仅含 `order_id`、`can_reserve`、`lines`；`lines` 合并本单重复 SKU 并按 SKU 升序覆盖该单全部商品，每行仅含 `sku`、`quantity`、`reserved`、`available`、`shortfall`（零缺口行也保留）。`quantity` 为本单当前订购量，`reserved` 为查询时本单实际预留量（缺少预留记录的旧数据为零），新增需求为 `quantity - reserved` 与零取较大值。各纳管商品初始余量取 stock 的 `available`（在库量减含其他订单在内的全部实际预留）；本单某商品的 `available` 是扣除先前**预计可补齐**订单新增需求后的余量。全部商品余量均能满足本单新增需求时 `can_reserve` 为 `true`，随后各商品余量扣除本单新增需求；任一商品不足时为 `false`，本单全部商品（即使某商品单独可满足）都不消耗余量，后续订单继续判断。`shortfall` 为新增需求减本单 `available` 与零取较大值，可补齐订单各行为零。任何订单已有预留都不释放、不转给其他订单，也不视为本单新增需求的额度。未纳管商品（含缺少库存记录的旧数据）不限制需求：`available` 为 `null`、`reserved` 和 `shortfall` 为零、不占用余量；暂停销售不阻止预览。查询成功或失败均不创建目录、改写文件或改变订单、库存、购物清单、历史及序号；相同数据和输入重复查询或重新打开同一 root 结果一致。预览不锁定库存，实际补齐仍以执行 `reserve-order` 当时的库存校验为准。
- `reservation-audit` → `OrderDesk.reservation_audit(sku)`。按商品核对库存占用的只读查询：直接列出当前持有该商品的待发货订单及账面预留与明细归属的差额，不执行补齐、释放或修正，不影响 `stock`、`pick-list` 及其他公开入口的既有行为。`sku` 去除首尾空白后区分大小写，非字符串、空白值或未知商品均抛出 `ValueError`；暂停销售仍可查询。结果仅含 `stock`、`allocated`、`difference`、`orders`：`stock` 与现有 `stock` 查询的完整结果一致（`{sku, on_hand, reserved, available}`，未纳管商品 `on_hand`、`available` 为 `null`、`reserved` 为零）。`orders` 按订单编号升序，只含状态为 `placed` 且当前商品行（合并重复 SKU 后）包含该商品的订单；取消、发货、签收的订单以及购物清单和退货记录均不进入明细；没有匹配订单时为空数组。每项仅含 `order_id`、`quantity`、`reserved`、`unreserved`，分别表示订单编号、合并重复 SKU 后的订购量、该单实际预留量及 `quantity - reserved` 与零取较大值；缺少预留记录时按零处理，预留量只取自当前预留记录，不从成交内容或历史推测，`unreserved` 也不扣减可用库存。`allocated` 为展示订单 `reserved` 的合计；`difference` 为 `stock` 的 `reserved` 减 `allocated`，保留正负号，零表示账面与明细相符。旧数据两者不一致时仍返回实际差额（如已不在该订单当前商品行中的遗留归属只计入账面、不进入明细），不修正库存或补造归属。未纳管商品（含缺少库存或预留集合的旧数据）沿用 `stock` 的空值语义：各订单 `reserved` 为零、`unreserved` 为订购量，遗留预留记录忽略，缺少订单集合时按空集合处理。补齐、释放、转移预留或改单后再次查询反映最新数量与归属。查询成功或失败均不创建目录、改写数据或消耗历史序号，重新打开同一 root 后结果一致。
- `transfer-reservation` → `OrderDesk.transfer_reservation(source_id, target_id, lines)`。在两笔待发货订单之间划转实际预留：来源订单把其持有的数量划给目标订单，不借用其他订单或可用库存，两单须不同且均为 `placed`。`source_id`、`target_id` 均为去除首尾空白后的非空字符串（区分大小写）；`lines` 为非空列表，每行含 `sku`（去除首尾空白后非空字符串，区分大小写）和正整数 `quantity`（不接受布尔值），行内额外字段忽略，重复 SKU 合并数量。编号非法、任一订单未知或状态不符、同单划转、清单非列表或为空、行非对象或缺少 `sku`/`quantity`、SKU 或数量非法均抛出 `ValueError`。涉及商品必须在目录中存在且已纳管（至少成功补货一次），并同时出现在两单的当前商品行中；商品未知、未纳管或未同时属于两单均整次拒绝，暂停销售不阻止划转。合并后的划转量不得超过来源订单该 SKU 的实际预留（缺少预留记录视为零），目标原预留加转入量不得超过其当前商品行合并订购量；来源不足或目标超量均抛出 `ValueError`。成功仅返回 `source_id`、`target_id`、`lines`，商品行按 SKU 升序，每行仅含 `sku`、`quantity`、`source_reserved`、`target_reserved`，后两项为划转后两单该 SKU 的实际预留。来源减量与目标增量同时生效：各商品在库量、总预留量、可用量及其他订单预留均不变，不新增库存历史；两单状态、成交行顺序、单价与金额保留，划转后两单预留记录中归零的 SKU 不留零值键。任一校验失败则整次拒绝，不写文件、不创建目录、不消耗历史序号；重复提交按提交当时两单余额重新判断。预留变更与两单历史同次保存到 `root/data.json`，重新打开结果一致：两单各追加一条 `action` 为 `transfer-reservation`、`result` 为完整返回快照的事件，序号各自接续该订单原历史，旧快照与已有 `complete` 不变，无历史的旧订单事件从 1 开始且 `complete` 为 `false`，不补造过去。划转后的拣货汇总与预留预览反映新归属，后续补齐、改单、取消和单笔及批量发货继续沿用各单实际预留规则，其他入口行为不变。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；单个转移请求整体成功或失败。
- `release-reservation` → `OrderDesk.release_reservation(order_id, lines)`。把一笔待发货订单的部分预留释放回可用库存，无需取消订单或指定接收订单：本单预留与商品总预留等量减少，可用量等量增加，在库量与其他订单预留不变，订单状态、商品行顺序及重复行、成交单价与金额保持不变，全部释放也保留订单。仅 `placed` 订单可释放；`order_id` 与 `sku` 均为去除首尾空白后的非空字符串（区分大小写）。`lines` 为非空列表，每行含 `sku` 和正整数 `quantity`（布尔值不接受），行内额外字段忽略，重复 SKU 合并数量。编号非法、未知订单、状态不符、列表类型错误或为空、行非对象或缺少 `sku`/`quantity`、SKU 非法、数量非法均抛出 `ValueError`。涉及商品必须在目录中存在、已纳管（至少成功补货一次）且属于该订单当前商品行；商品未知、未纳管或不属于订单均整次拒绝，暂停销售不阻止释放。合并释放量不得超过本单该 SKU 的实际预留（缺少预留记录的旧数据按零处理），预留不足抛出 `ValueError`。请求整体成功或拒绝：即使末项失败也不保留前项变更，不写文件、不创建目录、不追加历史或消耗序号；重复提交按当前余额重新判断。成功仅返回 `order_id` 和 `lines`，商品行按 SKU 升序，每行仅含 `sku`、`quantity`、`reserved`、`before`、`after`，分别表示商品、本次合并释放量、释放后本单剩余预留和释放前后 stock 的完整库存快照（`{sku, on_hand, reserved, available}`）；预留记录中归零的 SKU 不留零值键，本单全部释放时移除其预留记录。变更与历史同次保存到 `root/data.json`，重新打开一致：订单历史追加 `action` 为 `release-reservation`、`result` 为返回快照的事件，各涉及商品追加同名库存事件，`reference_id` 为订单编号，`before` 与 `after` 为本次库存快照，序号接续，旧快照与已有 `complete` 不变，无历史的旧数据从 1 开始且 `complete` 为 `false`，不补造过去。释放后的补齐、转移、改单、取消及单笔和批量发货继续按实际预留处理，拣货汇总与预留预览显示新余额，其他公开入口行为不变。命令外层 JSON 数组继续逐项独立执行，前项成功不因后项失败回滚；单个释放请求整体成功或失败。
- `list` → `OrderDesk.list_orders(...)`。参数名见 `core.py` 的公开方法签名。

命令成功向标准输出打印 JSON 并返回 0；输入或本地文件错误向标准错误输出说明并返回 2。无参数的方法可省略输入文件。数据保存在 `root/data.json`，每次成功修改后保存；适用于单进程本地使用。

## 样例

`examples/` 提供 3 份虚构业务样例。`tests/` 覆盖业务路径、拒绝非法操作后的状态和命令入口。

## 当前边界

当前仅支持一币种、一个商品目录、一次性取消、逐单与整批发货、离线签收确认（shipped → delivered，签收日期由调用方提供）、带原信息核对的发货记录更正（仅 shipped/delivered，原信息一致才可替换）、分次退货登记（不退款、不回补库存）、整笔退货入库（不退款、不分批入库）、已入库退货的整笔冲销（在库量按原凭据扣回、保留其后库存变动、不退款）、撤销尚未入库的退货登记（整笔撤销、不接受部分撤销）、跨订单只读退货处理清单、按商品的库存预留、placed 订单的预留补齐、两笔 placed 订单之间的预留转移、placed 订单的部分预留释放回可用库存、按指定订单优先顺序的预留补齐只读预览与批量执行、按商品核对库存占用与订单预留归属的只读查询、单笔订单履约数量（备货缺口与退货回库后净发出量）的只读总览、按承运商与运单号组合查找关联订单并合并履约数量的只读查询、整个 root 的只读履约金额汇总、库存盘点登记及按商品追溯库存变动。没有支付、拆单或物流联网功能。 不承诺并发写入或断电恢复。
